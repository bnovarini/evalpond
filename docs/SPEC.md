# evalpond - spec (v2, PM-audience edition)

An open-source, bring-your-own-tasks eval harness for LLM document pipelines. It ships with a demo task set: parsing and judging **synthetic** proof-of-income documents (pay stubs, bank statements).

Purpose: learn and demonstrate how eval loops work. Honest framing for the README: "I built this to learn how eval loops work." It is a small harness, not a production eval platform.

Name: TBD. `evalyard` is out (evalyard.com is a live LLM product). Bruno picks from candidates checked free on GitHub, PyPI and domains (evalpond, evalhatch, evalkiln, evalcairn, tinygrader). Use `evalpond` as a placeholder until chosen, then replace everywhere (package, CLI, docs).


## 0.5 Audience and product shape (v2 change)

Primary audience: product managers who need to understand evals, and who work with engineers shipping LLM features. Secondary: engineers who want a small readable harness.

What this changes, and what it does not:

- **The report is the product.** The engine (harness, grading hierarchy, stats) is unchanged from the rest of this spec. The value is a dashboard a PM can open, understand and act on without help.
- **Plain language first, numbers second.** Every verdict and statistic gets a one-line explanation in words, with the number shown beside it for people who want it.
- **Guided first run, about 10 minutes**, with no API keys needed (mock model), ending in a report the PM can click through.
- **README reads as a short guide to evals for PMs**, not a dev manual. Dev details move to docs/DEVELOPING.md.
- **Task set readable by non-engineers.** Opening a task shows what is being tested and why, in plain English, with no code.
- **Tool, not a course. Explicit boundary.** This is a working tool with a good report and one tight guide. Do NOT build tutorial pages, lesson sequences, quizzes, a glossary site or video content. Teaching lives inside the product (explanations next to numbers, a single GUIDE.md), not in a curriculum. If a feature request reads like "add a lesson", it is out of scope.

## 0. Ground rules (put these in the README, loudly)

1. Every document is synthetic. Generated by code in this repo. Names, employers, SSNs, account numbers and amounts are random and fictional.
2. No real borrower data, ever. No real employer, lender or payroll-provider formats, logos, field names, templates or internal terminology. Layouts are generic and invented here.
3. Nothing from any employer's material, tooling or data. This is public domain-knowledge only.
4. Every generated PDF/image carries a visible "SYNTHETIC - NOT A REAL DOCUMENT" watermark and metadata flag.
5. Provide a SECURITY/NOTICE section: do not submit real documents to this tool.

## 2. Task format

One JSON object per line in `tasks.jsonl`:

```json
{
  "id": "stub-017",
  "category": "extraction",
  "difficulty": "medium",
  "document": "docs/stub-017.pdf",
  "prompt_template": "extract_v1",
  "input_text_fallback": "docs/stub-017.txt",
  "expected": {"employer": "Harbor Lane Logistics", "gross_pay": 2314.50, "pay_period_start": "2026-03-01", "pay_period_end": "2026-03-14", "pay_frequency": "biweekly"},
  "grading": [
    {"method": "exact", "fields": ["employer","gross_pay","pay_period_start","pay_period_end","pay_frequency"], "normalize": "money_date_name"}
  ],
  "tags": ["multi-column", "ytd-present"]
}
```

- `document`: PDF or image. Adapters send it natively if the model supports it; otherwise use the `.txt` OCR-style fallback so text-only models can still run. Record which was used.
- Prompts live in versioned templates, not in tasks, so prompt changes are a separate variable from task changes.
- Each task has one or more `grading` entries, each with a method and weight.
- `manifest.yaml` records generator version, seed, task count, label counts. The set is fully reproducible from the seed.

## 3. Task set design: income_v1

About 60 tasks, built so a strong model scores 80-90% and a weak one 40-60% (otherwise nothing is measurable). Aim for a spread on purpose.

| Category | Count | Grading | What it tests |
|---|---|---|---|
| A. Field extraction, pay stubs | 20 | exact | employer, employee, gross pay, net pay, period dates, frequency, YTD |
| B. Field extraction, bank statements | 12 | exact | account holder, statement period, deposit list (date, amount, source) |
| C. Income calculation | 10 | exact + rubric | monthly income from stubs of varying frequency (weekly, biweekly, semi-monthly, monthly), with bonus/overtime lines |
| D. Completeness check | 8 | rubric | is the package sufficient (e.g. 2 stubs + 2 statements, covering required period)? what is missing? |
| E. Consistency / tamper signals | 10 | LLM-as-judge (+ exact on a verdict label) | does the doc contradict itself: YTD math, net != gross - deductions, dates out of order, font/format drift described in text layer, deposits not matching stub net |

Difficulty mix: 30% easy (clean single-column layout), 45% medium (multi-column, extra deductions, odd date formats, currency formatting), 25% hard (cross-document reasoning, ambiguous or missing fields, near-miss distractors such as two "gross" figures: current vs YTD).

Include negative cases: documents where the correct answer is "field not present" or "cannot determine". Scoring must reward abstaining correctly and penalize hallucination. Roughly 15% of tasks.

Hold out 20% as a "test" split never used when tuning prompts. Report dev and test separately. This teaches overfitting hygiene.

## 4. Grading

### 4.1 Exact match (structured fields)
- Normalize first: strip currency symbols and commas, parse dates to ISO, casefold and strip punctuation on names/employers, tolerance 0.005 on money.
- Score per field, report both field-level accuracy and task-level (all fields correct).
- Deterministic, no model calls. Unit-test the normalizers heavily.

### 4.2 Rubric
- A rubric is a list of binary criteria, each with a weight. Example for completeness: "identifies missing second stub", "names the uncovered date range", "does not claim the package is complete", "no invented documents".
- Two modes: (a) programmatic checks where possible (regex, set membership on a structured field the model must output), (b) model-checked criteria for the rest, one yes/no question per criterion, run via the judge adapter.
- Score = weighted fraction of criteria met. Show per-criterion results in the report so failures are diagnosable.

### 4.3 LLM-as-judge
- Used only where there is no crisp answer: the consistency/tamper explanations in category E.
- Judge sees task, ground-truth label and notes, and the candidate answer. It returns a JSON verdict with reasoning, then a score 0/1 (binary beats 1-10 scales for reliability).
- Controls to build in and teach in the README:
  - Judge model differs from the model under test (avoid self-preference).
  - Randomize order in any pairwise comparison (position bias).
  - Length-bias check: report correlation of judge score with answer length.
  - Calibration set: 20 hand-labeled answers by Bruno. Report judge-vs-human agreement (Cohen's kappa) in the report. If kappa is low, say so.
  - Temperature 0, cache judge calls by hash so reruns are free and stable.

Rule: prefer exact over rubric over judge. Use the cheapest, most deterministic grader that works.

## 5. Plugging models in

```python
class ModelAdapter(Protocol):
    name: str
    def run(self, prompt: str, document: DocumentRef) -> ModelOutput: ...
```

- `ModelOutput`: text, parsed JSON (if any), latency, input/output tokens, cost estimate, raw response, error.
- Adapters: Anthropic, OpenAI, a generic LiteLLM/OpenAI-compatible endpoint (covers local models), and `mock` (deterministic, scripted outputs for CI and demos, no API key).
- Config via `models.yaml`: name, adapter, model id, params, env var for the key. Keys never in the repo.
- Runner features: concurrency limit, retries with backoff, per-task timeout, resume a partial run, `--repeats N` to run each task multiple times (needed for noise estimates), and a cost cap that aborts a run.
- Every run saves one JSON file: model config, prompt template hash, task set version, git SHA, timestamps, per-task outputs and scores.

## 6. Visual report

Static site generated by `evalpond report runs/ --out site/`. Opens from a file or GitHub Pages link.

Views:
1. **Summary**: pass rate overall and by category and difficulty, with confidence intervals drawn as error bars. Cost and latency per model.
2. **Compare runs**: pick run A and run B. Show a paired table: tasks that flipped pass-to-fail (regressions, red), fail-to-pass (fixes, green), unchanged. Counts up top: "+5 fixed, -3 regressed, net +2, p=0.45, not significant".
3. **Task drilldown**: document preview, expected values, model output, grader result, per-field diff (expected vs got), judge reasoning where applicable.
4. **Heatmap**: tasks x models/runs, colored by score. Instantly shows which tasks discriminate (mixed colors) and which are dead weight (all pass or all fail).
5. **Judge health**: kappa vs human labels, length-bias plot.

Design: clean, single page, shareable deep links via URL hash (`#compare=runA,runB&task=stub-017`). Include a committed sample report from mock plus one or two real runs so the live demo link works without anyone running anything. Add an OG image for link previews, same as VortexYard.


### 6.1 PM-readable layer (v2 additions to the report)

Same engine and views as above, with this layer on top:

- **Verdict banner on every view**, in words: "Model B looks better than Model A on 8 tasks and worse on 3. The difference is too small to be sure (60 tasks is not many)." Verdict vocabulary is fixed: "likely better / no clear difference / likely worse". Never "better" off a point estimate alone.
- **One-line explainer next to every statistic**, hover or inline, never a wall of text. Examples: pass rate ("share of tasks answered fully right"); confidence interval ("the range the true pass rate probably falls in; wide range = don't read much into small gaps"); p-value shown as "chance this gap is luck"; flaky ("this task passed in some repeats and failed in others"); judge agreement ("how often the AI grader agrees with a human").
- **"What should I do with this?" box** on the compare view: plain suggestions such as "No clear difference. Ship on cost and latency, not accuracy" or "Regression on category C. Look at these 3 tasks first".
- **Task page in plain English**: "What this checks", "What a good answer looks like", the document, the model answer, and a green/red result with the reason in a sentence. Exact field diffs are secondary, behind a toggle.
- **Hide jargon by default**: terms like Wilson interval, McNemar, kappa appear only in an "Details for the curious" fold, each with a one-line definition.
- **Reading level check**: a test that scans report copy and fails if a banned-jargon term appears outside the details fold.

## 7. Statistical noise guidance (also goes in docs/NOISE.md)

Teach these directly in the report and docs:
- With n tasks and pass rate p, the standard error is about sqrt(p(1-p)/n). At n=60, p=0.8: roughly 5 points, so a 95% interval is about +/-10. A 3-point move means nothing. Show this number, not just the point estimate.
- Use Wilson intervals for pass rates (better than normal approximation near 0 or 1).
- For comparing two runs on the same tasks, use a paired test: McNemar's exact test on the flipped tasks, or a paired bootstrap on score differences. Only the discordant tasks carry information.
- Run-to-run variance: model outputs vary even at temperature 0 on some providers. Use `--repeats 3-5` and report the spread per task. A task that flips between repeats is flagged "flaky".
- Multiple comparisons: if you compare many prompts or models, some "wins" are luck. Say so in the report footer.
- Verdict language in the compare view: "likely better / no clear difference / likely worse", never "better" off a point estimate alone.
- Size guidance: to detect a 5-point change reliably you need hundreds of tasks. State that the demo set is for learning mechanics, not for fine decisions.

### 7.1 Task descriptions for non-engineers (v2)

Every task in `tasks.jsonl` gets two extra human-written-style fields, generated from templates and reviewed: `plain_title` ("Read the pay period dates from a two-column pay stub") and `why_it_matters` ("Underwriting needs the right period to count income correctly"). `tests/` check that every task has both and that neither contains code or field-name jargon.

## 8. Synthetic document generator

Goal: produce documents with known ground truth, varied layouts, and controllable defects.

**Pay stubs** (`generator/paystub.py`)
- Random fictional employer (name from a combinatorial generator, e.g. "Harbor Lane Logistics"), fictional employee, fake address, masked ID like `XXX-XX-0000` never a real pattern of a real person.
- Parameters: pay frequency, hourly vs salary, overtime, bonus, pre/post-tax deductions, YTD columns, state tax lines, period dates, pay date.
- 6-8 invented layout templates (single/multi column, table-heavy, compact, odd date formats, currency formats) rendered via HTML to PDF (WeasyPrint) with randomized fonts and spacing. Layouts are original designs, not copies of any payroll vendor.
- Math is computed so ground truth is internally consistent by default.

**Bank statements** (`generator/bank_statement.py`)
- Fictional bank ("Northfield Community Bank" style, invented), account holder, masked account number, statement period, opening/closing balance, 30-80 transactions with payroll deposits matching generated stubs (net pay, with realistic date offsets), plus noise: transfers, card purchases, other deposits that are NOT income (the distractors).
- 3-4 layouts.

**Defect injector** (`generator/inconsistencies.py`)
- Controlled, labeled defects for category E: YTD does not add up, net pay arithmetic wrong, period dates overlap or are out of order, deposit amount does not match stub net, employer name differs across docs, pay date on a weekend/holiday oddity, rounding anomalies.
- Each injected defect is recorded in the ground truth, so grading is mechanical for the verdict and the judge only assesses explanation quality.
- Important framing: these simulate internal inconsistencies for eval purposes. Do not build or document anything aimed at making documents look authentic to evade verification.

**Outputs**: PDF, PNG render, and a plain-text version (simulating an OCR text layer) plus `truth.json` per document. Seeded RNG, so `evalpond gen --seed 42 --n 60` always reproduces the same set. Watermark on every page.

## 10. Acceptance criteria

- `evalpond gen && evalpond run --model mock && evalpond report` works from a clean clone with no API keys.
- Same seed gives byte-identical task set.
- Compare view shows regressions and fixes between two runs, with interval and significance verdict.
- Every generated document is watermarked; a test fails the build if any is not.
- A grep test fails the build if repo contains known real-vendor names or flagged terms (maintain a small denylist file).
- The guided first run (`evalpond quickstart`) goes from clean clone to an open report in about 10 minutes with no API keys, printing each step in plain language.
- Every statistic in the report has a one-line plain explanation, and the compare view ends with a plain-language verdict and a suggested next step.
- A non-engineer can open any task and understand what it tests without reading code (checked by the plain_title / why_it_matters test).
- Repo contains no tutorial site, lesson content or quiz features (tool, not a course).
- README states the synthetic-only rule and the learning-project framing above the fold.
